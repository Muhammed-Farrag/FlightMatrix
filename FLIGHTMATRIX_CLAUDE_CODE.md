## Academic Requirements (OOP — Must Be Reflected in Code)

### Mandatory OOP Principles

1. **Inheritance**
   - Abstract base class `User` with `userId`, `username`, `password`, `name`, `email`, `contactInfo`
   - `Customer extends User` — adds `address`, `bookingHistory`, `preferences`
   - `Agent extends User` — adds `agentId`, `department`, `commission`
   - `Administrator extends User` — adds `adminId`, `securityLevel`
   - `Flight` hierarchy: base `Flight` → `DomesticFlight`, `InternationalFlight`
   - `Booking` as extendable base class

2. **Encapsulation**
   - All entity fields must be `private`
   - Access via getters/setters with validation logic
   - Password field: write-only (no plain getter)
   - Payment details hidden from other components

3. **Polymorphism**
   - `calculatePrice()` behaves differently per seat class and flight type
   - `generateTicket()` produces different output per booking type
   - Payment methods handled through a common interface

4. **Abstraction**
   - `User` must be an abstract class
   - `PaymentProcessor` interface implemented by `CreditCardProcessor`, `BankTransferProcessor`
   - Complex fare rules hidden behind `calculateFare()` method

5. **Class Relationships**
   - `Customer` has-many `Booking`
   - `Flight` has-many `Seat`
   - `Booking` has-many `Passenger`
   - `BookingSystem` is the central coordinator class

### Required Key Classes

| Class | Type | Key Attributes | Key Methods |
|---|---|---|---|
| `User` | Abstract | userId, username, password, name, email, contactInfo | login(), logout(), updateProfile() |
| `Customer` | Extends User | customerId, address, bookingHistory, preferences | searchFlights(), createBooking(), viewBookings(), cancelBooking() |
| `Agent` | Extends User | agentId, department, commission | manageFlights(), createBookingForCustomer(), modifyBooking() |
| `Administrator` | Extends User | adminId, securityLevel | createUser(), modifySystemSettings(), manageUserAccess() |
| `Flight` | Entity | flightNumber, airline, origin, destination, departureTime, arrivalTime, availableSeats, prices | checkAvailability(), updateSchedule(), calculatePrice(), reserveSeat() |
| `Booking` | Entity | bookingReference, customer, flight, passengers, seatSelections, status, paymentStatus | addPassenger(), calculateTotalPrice(), confirmBooking(), cancelBooking(), generateItinerary() |
| `Passenger` | Entity | passengerId, name, passportNumber, dateOfBirth, specialRequests | updateInfo(), getPassengerDetails() |
| `Payment` | Entity | paymentId, bookingReference, amount, method, status, transactionDate | processPayment(), validatePaymentDetails(), updateStatus() |
| `BookingSystem` | Service/Coordinator | users, flights, bookings, payments | searchFlights(), createBooking(), processPayment(), generateTicket() |

### Role-Based Access

- **Customer:** Search flights, create/view/cancel bookings, complete payment, view e-ticket
- **Agent:** All customer actions + manage flight inventory, create bookings for customers, generate reports
- **Administrator:** All agent actions + manage users, system settings, view logs

## Technical Specifications

### Backend

- **Framework:** Spring Boot 3.x
- **Language:** Java 17+
- **Database:** SQLite via `sqlite-jdbc` + Spring Data JPA + Hibernate
- **Auth:** Spring Security with session-based authentication
- **Build:** Maven (`pom.xml`)
- **Lombok:** Yes — use `@Data`, `@Builder`, `@NoArgsConstructor`, `@AllArgsConstructor`

### Database

- **File:** `flightmatrix.db` at project root
- **DDL:** Auto-generated by Hibernate (`spring.jpa.hibernate.ddl-auto=update`)
- **Tables:** `users`, `flights`, `bookings`, `passengers`, `payments`, `seats`

- **Pure HTML/CSS/JS** — no React, no Vue, no framework
- **Fonts (Google Fonts):** Plus Jakarta Sans (headings), Inter (body), JetBrains Mono (data/codes)
- **Icons:** Lucide Icons (thin-line, 1–1.5px stroke, never filled unless active toggle)
- **API calls:** Native `fetch()` to Spring Boot REST endpoints
- **Layout:** Fixed top navbar + page content area

## Phase 1 — Foundation (Project Setup + Entities)

### Goal
Scaffold the Spring Boot project, configure SQLite, and implement all JPA entity classes with correct OOP hierarchy.

### Tasks

**1.1 — `pom.xml`**
- Spring Boot Starter Web
- Spring Boot Starter Data JPA
- Spring Boot Starter Security
- `sqlite-jdbc` (org.xerial, latest stable)
- `hibernate-community-dialects` for SQLite dialect
- Lombok
- Spring Boot DevTools

**1.2 — `application.properties`**
```properties
spring.datasource.url=jdbc:sqlite:flightmatrix.db
spring.datasource.driver-class-name=org.sqlite.JDBC
spring.jpa.database-platform=org.hibernate.community.dialect.SQLiteDialect
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
server.port=8080
```

**1.3 — Enums**
Create all enums in `com.flightmatrix.enums`: `UserRole`, `BookingStatus`, `PaymentStatus`, `SeatClass`, `PaymentMethod`

**1.4 — Entity Classes**
- `User` → `@MappedSuperclass` or `@Inheritance(strategy=SINGLE_TABLE)` abstract class
- `Customer`, `Agent`, `Administrator` → extend `User` with `@Entity`
- `Flight` → base entity, extended by `DomesticFlight` and `InternationalFlight`
- `Booking` → references `Customer` (ManyToOne) and `Flight` (ManyToOne)
- `Passenger` → references `Booking` (ManyToOne)
- `Payment` → references `Booking` (OneToOne)
- `Seat` → references `Flight` (ManyToOne), has `SeatClass` and `isAvailable`

**1.5 — PaymentProcessor Interface**
```java
public interface PaymentProcessor {
    boolean processPayment(Payment payment);
    boolean validatePaymentDetails(Payment payment);
    void updateStatus(Payment payment, PaymentStatus status);
}
```
Implement with `CreditCardProcessor` and `BankTransferProcessor`.

**1.6 — `FlightMatrixApplication.java`**
Main entry point with `@SpringBootApplication`. Add a `CommandLineRunner` bean that seeds sample data (2 flights, 1 customer, 1 agent, 1 admin) if the DB is empty.

### Deliverable
Running Spring Boot app that starts without errors, creates `flightmatrix.db` with all tables, and seeds sample data.

## Phase 2 — Backend (Repositories + Services + Controllers)

### Goal
Build the full REST API layer. All business logic in services, thin controllers, clean DTOs.

### Tasks

**2.1 — Repositories**
Create JPA repository interfaces for all entities. Add custom query methods:
- `FlightRepository`: `findByOriginAndDestinationAndDepartureDate()`
- `BookingRepository`: `findByCustomerId()`, `findByBookingReference()`
- `UserRepository`: `findByUsername()`

**2.2 — DTOs**
- `LoginRequest` — username, password
- `FlightSearchRequest` — origin, destination, date, seatClass, passengerCount
- `BookingRequest` — flightId, seatClass, passengers list, specialRequests
- `PaymentRequest` — bookingReference, method, amount, cardDetails (if credit card)
- `ApiResponse<T>` — generic wrapper: success, message, data

**2.3 — Services**

`UserService`
- `register(RegisterRequest)` — validate password (min 6 chars, letters + numbers), hash password, save
- `authenticate(LoginRequest)` — validate credentials, return user role
- `updateProfile(userId, profileData)`

`FlightService`
- `searchFlights(FlightSearchRequest)` — filter by origin, destination, date, seat availability
- `addFlight(FlightRequest)` — agent/admin only, validate no duplicate flight numbers
- `updateFlight(flightNumber, updates)`
- `calculatePrice(flightId, seatClass)` — polymorphic: different logic per class

`BookingService`
- `createBooking(BookingRequest, customerId)` — generate PNR (format: `FM-XXXXXX`), status = RESERVED
- `confirmBooking(bookingReference)` — status = CONFIRMED
- `cancelBooking(bookingReference)` — status = CANCELLED, release seats
- `generateItinerary(bookingReference)` — return full booking details

`PaymentService`
- `processPayment(PaymentRequest)` — delegate to correct `PaymentProcessor` impl
- `validatePaymentDetails(PaymentRequest)` — check card format, amount > 0
- `getPaymentStatus(bookingReference)`

`BookingSystem` (Central Coordinator)
- Orchestrates across services
- `searchFlights()`, `createBooking()`, `processPayment()`, `generateTicket()`
- This class satisfies the OOP requirement for the `BookingSystem` coordinator

**2.4 — Controllers**

`AuthController` — POST `/api/auth/login`, POST `/api/auth/logout`, POST `/api/auth/register`

`FlightController` — GET `/api/flights/search`, GET `/api/flights/{id}`, POST `/api/flights` (agent+), PUT `/api/flights/{id}` (agent+), GET `/api/flights/all` (agent+)

`BookingController` — POST `/api/bookings`, GET `/api/bookings/{reference}`, GET `/api/bookings/my`, PUT `/api/bookings/{reference}/cancel`

`PaymentController` — POST `/api/payments/process`, GET `/api/payments/{reference}`

`AdminController` — GET `/api/admin/users`, POST `/api/admin/users`, DELETE `/api/admin/users/{id}`, GET `/api/admin/logs`

**2.5 — Security Config**
- Permit: `/`, `/api/auth/**`, `/css/**`, `/js/**`, `/assets/**`
- Require auth: all `/api/**` routes
- Role guards: `/api/admin/**` → ADMIN only, `/api/flights` POST/PUT → AGENT or ADMIN
- Use `HttpSession` for auth state (no JWT needed for this scope)

### Deliverable
Full REST API testable via browser or Postman. All endpoints returning `ApiResponse<T>` JSON.

## Notes for Claude Code

- Always use `var(--css-variable)` for colors, never hardcode hex values in CSS
- `JetBrains Mono` must be applied via `.data-mono` class or inline `font-family` — never forget it for prices and codes
- Spring Security CSRF: disable for REST API routes or handle token in JS
- SQLite does not support all Hibernate features — avoid `GenerationType.SEQUENCE`, use `GenerationType.IDENTITY`
- When in doubt about OOP structure, favor explicit class hierarchies over convenience shortcuts — this is graded
- PNR format: `FM-` followed by 6 random alphanumeric characters (e.g., `FM-A3K9PX`)
- Booking reference and PNR are the same field
